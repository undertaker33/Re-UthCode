## 3. 当前任务目标

### 3.1 最终交付

T04 完成后必须具备：

1. Core 自有的 Tool Protocol、稳定 Registry、JSON Schema 校验和严格 FIFO Executor；
2. 六个默认 Integration Tool：
   - `ReadFile`
   - `WriteFile`
   - `EditFile`
   - `Glob`
   - `Grep`
   - `Bash`
3. 统一工作区路径解析和符号链接越界防护；
4. 共享文件读取状态，支持 read-before-write/edit；
5. 内容摘要与文件状态联合校验，能够发现 mtime 被恢复后的内容变化；
6. 统一、确定性的工具输出截断；
7. 超时与取消时能够终止并回收命令子进程；
8. Application 统一暴露工具定义和 ToolCall 执行入口；
9. 正式 `create_application()` 默认按固定顺序装配六个工具；
10. Headless 调用方可以手动完成“模型产生 ToolCall → 执行 → ToolResult 回填”的单次工具往返；
11. 配置加载依赖恢复单向，Integration 不再导入 Application；
12. 离线 Core、Integration、Application、三 Provider 回归与架构测试。

### 3.2 明确不交付

本任务不实现：

- 自动 ReAct Agent Loop；
- Provider 完成后自动提取、执行并再次请求模型；
- RunState、TurnState、最大轮数、预算、恢复和终态状态机；
- Permission 的 Allow、Deny、Ask；
- 危险命令判断和人工审批；
- OS Sandbox；
- 工具并行执行；
- deferred/discovered Tool；
- Tool enable/disable 配置；
- MCP、Skill、Hook、Memory、Context、Subagent；
- TUI Tool 状态卡、权限弹窗或工具调用交互；
- 跨 Run 工具输出仓库；
- System Prompt 对工具能力的自动声明。

### 3.3 最小可运行调用链

```text
Headless Caller
      │
      ├── application.tool_definitions()
      │             │
      │             ▼
      │       Core ToolRegistry
      │
      ├── GenerationRequest(
      │       tools=application.tool_definitions()
      │   )
      │             │
      │             ▼
      │       Provider Integration
      │             │
      │             ▼
      │       ToolCallPart[]
      │
      └── application.execute_tool_calls(calls)
                    │
                    ▼
             Core ToolExecutor
                    │  strict FIFO
                    ▼
       Integration File/Search/Process Tool
                    │
                    ▼
             ToolResultPart[]
```

调用方可以将 Assistant ToolCall 消息和 `Message(role="tool")` 的结果追加到下一次请求。T04 不替调用方自动循环。

### 3.4 自动暴露边界

现有 CLI/TUI 尚不能消费 ToolCall 并继续循环，因此：

- `UthCodeApplication.start_generation()` 不得自动向所有请求注入默认工具；
- CLI/TUI 当前生成链路保持不变；
- Headless 调用方必须显式把 `application.tool_definitions()` 放入 `GenerationRequest.tools`；
- T05 Agent Loop 应复用同一 Registry、Executor 和 Application Tool API，再负责自动暴露和循环；
- 不得为 T05 创建空 Runtime、Loop、State 或事件占位。

### 8.2 工具数据所有者

| 数据 | 权威所有者 | 说明 |
| --- | --- | --- |
| Tool schema | `core.provider.ToolDefinition` | Provider 无关 |
| Tool call | `core.provider.ToolCallPart` | 保留 Provider 返回的 call ID |
| Tool result message | `core.provider.ToolResultPart` | 每个 call 一一对应 |
| Tool runtime contract | `core.tool.Tool` | Integration 具体工具实现该 Protocol |
| 工具目录顺序 | `core.tool.ToolRegistry` | 注册顺序即暴露顺序 |
| 参数校验 | `core.tool.ToolExecutor` | 使用 ToolDefinition JSON Schema |
| 工作目录 | `ApplicationRuntimeContext.workdir` | 默认工具装配唯一事实 |
| 文件读取状态 | 每个 Application 的 `FileReadTracker` | Run-local，不跨 Application 全局共享 |
| 配置最终模型 | `application.configuration.EffectiveConfig` | Integration 不构造 |
| 配置原始读取结果 | `integrations.config.data.LoadedConfigData` | 转换后不保留为第二份运行配置 |

### 8.3 ToolCall 执行流程

```text
ToolCallPart[]
      │
      ▼
ApplicationToolService
      │
      ▼
ToolExecutor.execute_batch()
      │
      ├── cancellation pre-check
      ├── Registry 按 name 查找
      ├── JSON Schema 参数校验
      ├── await Tool.execute()
      ├── 普通异常 → is_error ToolResultPart
      ├── 统一输出截断
      └── 下一调用
      │
      ▼
ToolResultPart[]  # 数量、顺序、call ID 与输入一致
```

### 8.4 FIFO 与取消

必须满足：

- 一个 batch 内一次只执行一个工具；
- 不因 read-only 工具而并行；
- 当前工具普通失败后继续执行后续调用；
- 取消后不再启动新的工具；
- 尚未执行的每个调用仍获得对应取消结果；
- 文件写入/编辑在实际副作用前再次检查取消；
- 已开始的普通文件操作不得被盲目重试；
- 已开始的 Bash 在 timeout/cancel 时终止进程组或进程树并等待回收；
- 无法确认 Bash 子进程是否终止时必须向上返回明确错误，不得报告成功。

### 8.5 参数校验边界

- 每个 Tool 通过 `ToolDefinition.parameters` 提供完整 JSON Schema；
- Registry 注册时使用 `jsonschema` 检查 schema 本身合法；
- Executor 执行前验证 `ToolCallPart.arguments`；
- Tool 实现只接收已经过 schema 校验的 `JsonPayload`；
- `jsonschema` 的异常对象不得出现在 Application API；
- 错误内容只保留稳定前缀和必要字段路径，不锁定第三方库全文。

### 8.6 工作区边界

```text
ApplicationRuntimeContext.workdir
            │
            ▼
WorkspacePathResolver.root (absolute physical path)
            │
            ├── existing path: strict resolve + relative_to(root)
            ├── new path: validate nearest existing parent physical path
            ├── candidate file: lexical + resolved 双重检查
            └── display: root-relative POSIX-style path
```

要求：

- 拒绝空字节；
- 拒绝工作区外绝对路径；
- 拒绝 `..` 逃逸；
- 拒绝指向工作区外目标的文件或目录符号链接；
- Glob/Grep 不跟随目录符号链接；
- 搜索结果按相对路径稳定排序；
- 路径限制是文件工具自身边界，不代表 Bash 被沙箱化。

### 8.7 文件状态隔离

每个正式 Application 创建：

```text
1 WorkspacePathResolver
1 FileReadTracker
3 file tools sharing the same tracker
```

`FileReadTracker` 至少保存：

- 规范化物理路径；
- 文件内容摘要；
- 文件大小；
- mtime_ns；
- 可用于识别替换的 stat 身份信息（平台可用时）。

校验时重新读取或摘要内容。即使 mtime 被恢复，只要内容变化也必须拒绝写入或编辑。

### 8.8 配置数据流

修复后：

```text

        │ primitive cwd/home/model
        ▼
Integration load_config_data()
        │
        ├── discover
        ├── TOML parse

        ▼

        │

        │
```

`LoadedConfigData` 在转换后不成为第二套运行配置对象。

### 8.9 冻结的 Core Tool API

实施应采用以下等价公开契约；允许调整私有 helper，不得增加无调用方字段：

```python
@dataclass(frozen=True, slots=True)
class ToolExecutionResult:
    content: str
    is_error: bool = False


@runtime_checkable
class Tool(Protocol):
    @property
    def definition(self) -> ToolDefinition: ...

    async def execute(
        self,
        arguments: JsonPayload,
        *,
        cancellation: CancellationToken,
    ) -> ToolExecutionResult: ...


class ToolRegistry:
    def register(self, tool: Tool) -> None: ...
    def get(self, name: str) -> Tool | None: ...
    def list_tools(self) -> tuple[Tool, ...]: ...
    def definitions(self) -> tuple[ToolDefinition, ...]: ...


class ToolExecutor:
    async def execute_call(
        self,
        call: ToolCallPart,
        *,
        cancellation: CancellationToken,
    ) -> ToolResultPart: ...

    async def execute_batch(
        self,
        calls: Sequence[ToolCallPart],
        *,
        cancellation: CancellationToken,
    ) -> tuple[ToolResultPart, ...]: ...
```

约束：

- `Tool.definition.name` 是唯一注册键；
- `ToolExecutionResult` 不包含 metadata、elapsed、permission 或 provider 字段；
- `ToolRegistry.get()` 对未知名称返回 `None`，未知工具由 Executor 规范化；
- 所有公开集合返回 tuple；
- 默认最大结果长度为 `10_000` 字符；
- 截断标记必须稳定且只能追加一次；
- schema 与 arguments 在校验前转换为普通 JSON dict/list，不能把 `JsonPayload` 或 `FrozenList` 的实现细节交给第三方 Validator。

### 8.10 冻结的 Application Tool API

```python
class UthCodeApplication:
    def tool_definitions(self) -> tuple[ToolDefinition, ...]: ...

    async def execute_tool_calls(
        self,
        calls: Sequence[ToolCallPart],
        *,
        cancellation: CancellationToken | None = None,
    ) -> tuple[ToolResultPart, ...]: ...


def create_application(
    config: EffectiveConfig,
    *,
    provider_builder: ProviderBuilder | None = None,
    model_writer: ModelWriter | None = None,
    runtime_context: ApplicationRuntimeContext | None = None,
    tools: Sequence[Tool] | None = None,
) -> UthCodeApplication: ...
```

语义：

- `tools is None`：正式组合根按 runtime workdir 创建六个默认工具；
- 显式传入 `tools`：完整替代默认集合，用于 Embedded 或测试，不与默认集合合并；
- `execute_tool_calls()` 未传 token 时为该 batch 创建独立 token；
- `start_generation()` 不自动注入 `tool_definitions()`；
- Application 不返回 Registry、Executor 或 concrete Integration Tool。

### 8.11 默认工具名称与参数 Schema

| 名称 | 必填参数 | 可选参数 | 关键限制 |
| --- | --- | --- | --- |
| `ReadFile` | `path: string` | `offset: integer = 1`、`limit: integer = 2000` | offset ≥ 1，1 ≤ limit ≤ 2000 |
| `WriteFile` | `path: string`、`content: string` | 无 | `additionalProperties=false` |
| `EditFile` | `path: string`、`old_string: string`、`new_string: string` | 无 | old_string 非空且唯一 |
| `Glob` | `pattern: string` | `path: string = "."` | pattern 必须为相对模式，禁止空字节和 `..` 段 |
| `Grep` | `pattern: string` | `path: string = "."`、`include: string | null` | Python regex；include 为相对文件模式 |
| `Bash` | `command: string` | `timeout_seconds: integer = 120` | 1 ≤ timeout ≤ 600 |

全部 schema：

- 顶层 `type` 为 `object`；
- 显式 `required`；
- `additionalProperties` 为 `false`；
- 名称与参数结构在 T04 完成后作为 T05 的稳定输入。

### 8.12 配置 Raw Data API

`providers` 和 `models` 必须在返回前深拷贝并冻结；其字段使用 `EffectiveConfig.from_mapping()` 已有的 canonical raw mapping 名称。

## 13. 验收标准

全部满足才可验收。

### 13.1 功能

- 六个默认工具均可通过正式 Application API 执行；
- Registry 顺序稳定且拒绝重复名；
- 参数由 ToolDefinition JSON Schema 统一校验；
- 每个 ToolCall 都得到相同 ID 的 ToolResult；
- batch 严格 FIFO；
- 普通错误不导致整个 batch 崩溃；
- 文件、搜索和 Bash 输出受统一长度限制；
- Headless Fake 链路完成一次手动工具往返。

### 13.2 文件安全

- 所有文件和搜索路径限制在 runtime workdir；
- `..`、外部绝对路径、文件 symlink、目录 symlink 均不能逃逸；
- Glob/Grep 对每个候选进行物理路径验证；
- 已有文件未读时不能 Write/Edit；
- 内容变化即使 mtime 恢复也能识别；
- 写入或编辑成功后 tracker 刷新。

### 13.3 进程语义

- Bash 使用当前 OS shell、当前用户权限和 runtime workdir；
- timeout/cancel 后进程被终止并回收；
- stdout、stderr、无输出和退出状态可区分；
- README 和代码均不把 Bash 描述为 Sandbox；
- 不存在危险命令黑名单或审批伪实现。

### 13.4 架构

- Core 不依赖 Application、Integration、Interface 或 Provider SDK；
- Integration 不依赖 Application 或 Interface；
- Interface 不依赖 Core Tool 或 Integration Tool；
- Application 是 Headless 工具统一入口；
- concrete file/process Tool 只在 Integration；
- `ToolDefinition`、`ToolCallPart`、`ToolResultPart` 没有重复定义；
- 第三方 `jsonschema` 类型不越过 Core；
- 删除 Interface 后 Headless 工具 E2E 仍能运行。

### 13.5 配置回归

- Integration 只返回 `LoadedConfigData`；
- Application 构造 `EffectiveConfig`；
- 用户/项目/CLI 配置优先级不变；
- 项目配置秘密与 Provider 重定向继续硬失败；
- 缺失模板、path/field 错误证据和模型写回行为不变；
- 架构测试能够捕获任意新的 `integrations → application` import。

## 14. 编码停止条件

遇到以下情况必须停止相关范围并报告：

- 实施需要修改 `ToolDefinition`、`ToolCallPart`、`ToolResultPart` 的冻结字段；
- 必须改变 Provider ToolCall 统一语义才能继续；
- 需要自动执行 Provider ToolCall 或新增 Agent Loop；
- 需要引入 Permission、审批、危险命令策略或 Sandbox；
- 需要让 Interface 直接导入 Core Tool 或 Integration Tool；
- 需要让 Integration 再次导入 Application；
- 需要让 Core 依赖文件系统具体实现、进程实现或 Provider SDK；
- JSON Schema 无法表达某工具参数，必须新增第二套参数模型；
- 文件操作是否已经产生副作用无法确认且实现试图盲目重试；
- Bash timeout/cancel 后无法确认子进程已收口，却准备返回成功；
- 需要放宽工作区边界才能通过测试；
- 需要实现 deferred、并行、MCP 或后续能力才能完成当前任务；
- 需要整文件复制旧 UthCode 或 MewCode；
- 实际修改文件明显超出本任务目录树；
- 当前基线源码与已完成任务包出现新的实质差异；
- 两项冻结决策发生冲突。

以下不属于停止条件，应由编码代理自行解决：

- 普通编译错误；
- 单元测试失败；
- JSON Schema 编写错误；
- 跨平台测试适配；
- 私有函数拆分；
- 错误文本的局部整理；
- lint、类型和格式问题。
