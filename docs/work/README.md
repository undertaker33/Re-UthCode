## 工作包拆分规则

`docs/work/` 只存放仍活跃的正式工作包。工作完成并经用户确认后，由用户手动移动至 `docs/archive/work/`，Agent 不得自行归档。

### 1. 接收需求文件

收到需求文件后：

1. 在 `docs/work/` 下创建与需求文件同名、去除后缀的目录；
2. 将原始需求文件移动到该目录并保留；
3. 根据需求中提及的源码、报告、实验、教程及官方资料进行验证；
4. 找出会影响范围、架构、行为或验收方式的待确认项；
5. 对每个待确认项给出可选方案、影响和推荐方案；
6. 全部确认完成后，再生成正式工作包。

目录示例：

```text
docs/work/T01-provider/
├── T01-provider.md
├── T01-provider-spec.md
├── T01-provider-tasks.md
└── T01-provider-checklist.md
```

文件名前缀 `TXX-xxxx` 必须与原始需求文件保持一致。

### 2. `TXX-xxxx-spec.md`

回答：**做什么、为什么做、做到什么程度。**

必须包含：

- 背景；
- 目标；
- 按 Task 划分的能力清单；
- 非功能要求；
- 设计骨架；
- Out of Scope；
- 验收标准。

不得包含具体函数名、参数名、默认值、错误文本、源码行号、SDK 内部类型或逐文件实现步骤。

### 3. `TXX-xxxx-tasks.md`

回答：**按什么顺序实施、每步修改什么。**

文件顶部必须说明强相关 Task 的 Worker 分组。一个 Worker 应严格串行完成一组强相关 Task，而不是只开发单个 Task。任务只能由用户显式指派后开始。

每个 Task 必须包含：

- 任务目标；
- 新增、修改、删除的文件；
- 各文件职责和实施内容；
- 依赖任务；
- 参考资料定位，尽量精确到文件、符号、测试或文档章节；
- 完成边界。

单个 Task 应能在一个专注会话中完成。不得仅按文件数量拆分。

任务序列最后必须包含：

- `[接入主流程]`：接入正式调用链并清理被替代的旧入口；
- `[端到端验证]`：从真实入口验证正常路径和关键失败路径。
- `[遗留负担清理]`: 用于确认本工作包没有引入或保留 1.面向旧类、旧 API、旧行为的兼容层；2.已被替代的旧入口、旧实现和不可达代码；3.职责重叠的模块、协议或数据结构；4.与现有能力重复的实现；5.仅为兼容 Re 早期实现而存在的逻辑。

### 4. `TXX-xxxx-checklist.md`

Checklist 必须与 `tasks` 中的 Task 顺序和编号一一对应。

每项必须：

- 可执行；
- 可观测；
- 可明确判断通过或失败；
- 能作为该 Task 的完成证据。

推荐写法：

```text
- [ ] 执行 `pytest ...`，全部用例通过。
- [ ] 执行 `grep -r "LegacyX" src tests`，返回 0 条。
- [ ] 输入 X 后，通过正式入口观察到输出 Y。
```

禁止使用：

```text
实现完整
质量良好
架构合理
功能正常
测试充分
```

每份 Checklist 至少包含一条端到端验收，并分别覆盖 `[接入主流程]` 和 `[端到端验证]`。

### 5. 一致性要求

三份文件必须满足：

```text
spec 中的能力
→ tasks 中有对应实施任务
→ checklist 中有对应验收证据
```

Task 编号、顺序和命名必须一致。Out of Scope 不得进入实施任务，未经用户确认的重大决策不得被写成既定方案。
