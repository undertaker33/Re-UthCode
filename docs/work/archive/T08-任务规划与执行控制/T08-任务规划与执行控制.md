## 1.4 当前行为事实

当前主执行链：

```text
User Input
  ↓
AgentRun.start_turn
  ↓
AgentLoop.start_turn
  ↓
AgentTurnExecution.run_segment
  ↓
Provider iteration
  ├─ ToolCall → prepare → Permission → execute → next iteration
  └─ final    → commit assistant → TurnCompleted
```

当前存在以下能力缺口：

1. 没有一等 Behavior Mode；Runtime 无法表达“当前 Agent 在规划”或“当前 Agent 在实施”。
2. 没有 Plan proposal / review / revision / approval 协议。
3. 没有结构化 Todo/TaskState，长执行只能依靠自然语言上下文维持进度。
4. 没有执行中的持续规划与重规划协议。
5. active Turn 期间用户无法通过正常输入追加或修改当前任务；现有 pause 只能暂停/恢复原任务。
6. Provider final 只有普通完成语义，无法被 Plan Review 或未完成 Task 拦截。
7. Tool runtime 没有正式的 Behavior Mode pre-tool 拦截点。
8. TUI 没有 Behavior Mode、Plan、Todo、Steering 的完整投影。

## 1.5 机制参考

本任务采用以下已经验证适合 UthCode 的机制：

- Plan Mode 是独立行为模式，不等价于 Todo。
- Plan Mode 允许只读探索、计划修改、用户审批，批准后进入实施。
- Provider-facing Tool View 与 Runtime fail-closed 检查同时存在。
- Todo 是执行期结构化工作状态，模型显式维护。
- Plan 与 Todo 不自动互相转换。
- Runtime 只维护明确状态与控制边界，不使用“工具次数、文件数量、任务长度”等启发式判断任务复杂度。

# 二、任务定位

T08 的目标不是实现一个 Workflow Engine，而是让现有单 AgentLoop 具备完整的任务规划与执行控制能力。

完成后，UthCode 的单 Turn Runtime 必须能够表达并闭合以下行为：

```text
用户目标
  ↓
Behavior Mode
  ├─ PLAN    → 探索 / 澄清 / 设计 / Plan Review
  └─ DEFAULT → 探索 / 实施 / 验证 / Execution Planning

DEFAULT 执行期间：
  TaskState 记录当前执行事实
  User Steering 可追加/修改当前用户目标
  模型根据新事实更新或重写 TaskState
  Completion Hook 阻止带未完成 Task 的虚假完成
```

本任务必须保持：

```text
一个 AgentLoop
一个 active Turn
一个 RunState authority
```

Behavior Mode、Execution Planning、Steering、Hook 都是这条 Loop 的能力，不创建第二套执行器。

# 三、最终能力模型

T08 完成后形成六个相互配合但职责独立的能力：

```text
1. Behavior Mode
   DEFAULT / PLAN

2. Plan Workflow
   Research → Plan Proposal → Review → Revise/Approve

3. Todo / TaskState
   执行中的结构化任务事实

4. Execution Planning（持续执行/长任务规划）
   执行中的持续推进、计划更新、重规划、失败恢复

5. User Steering
   active Turn 中用户主动追加/修改当前目标

6. Runtime Hook
   当前真实生命周期拦截点：
   - before_tool_execution
   - before_completion
```

其中：

- Plan Workflow 解决“实施前怎么计划并获得用户批准”。
- Execution Planning 解决“实施过程中怎么持续知道下一步做什么并适应新事实”。
- Todo/TaskState 是 Execution Planning 的结构化状态载体之一。
- User Steering 把用户中途输入变成当前 Turn 的真实用户事实。
- Runtime Hook 提供少量确定性的生命周期拦截，不负责主动调度 Agent/Tool。

# 四、Behavior Mode

## 4.1 Core 类型

新增：

```text
BehaviorMode.DEFAULT
BehaviorMode.PLAN
```

Core 内部统一使用 `DEFAULT` 与 `PLAN`。

产品/UI 语义：

```text
DEFAULT = 默认 / 构建 / 实施模式
PLAN    = 规划模式
```

Slash Command：

```text
/plan  → PLAN
/do    → DEFAULT
/build → /do alias
```

## 4.2 Behavior Mode 是一等 Runtime 状态

Behavior Mode 必须影响：

```text
Behavior Mode
  ├─ Agent 行为目标
  ├─ Runtime Prompt Facts
  ├─ Provider-facing Tool View
  ├─ before_tool_execution Hook 行为
  ├─ Provider final 语义
  ├─ Plan Review / Resume 路径
  ├─ Completion 语义
  └─ Interface 投影
```

因此 Mode 不允许仅由 TUI、Tool filter 或 prompt string 表示。

## 4.3 状态所有权

建议最终状态关系：

```text
AgentRun
  └─ idle_behavior_mode

active Turn / RunState
  └─ behavior_mode
```

规则：

- 新 Run 默认 `DEFAULT`。
- 没有 active Turn 时，`/plan` 与 `/do` 修改该 Run 下一 Turn 的 Behavior Mode。
- Turn 开始时，Behavior Mode 进入 Core 权威执行状态。
- active Turn 期间，Interface 不能直接修改 Core mode。
- Plan Review `APPROVE` 是 active Turn 内允许发生的正式 `PLAN → DEFAULT` transition。
- Turn 结束后，AgentRun 同步 Core 最终 Behavior Mode，供下一 Turn 使用。

## 4.4 与 Permission Mode 正交

状态空间是：

```text
Behavior Mode: DEFAULT | PLAN
Permission Mode: default | auto | full_access
```

二者互不替代。

例如：

```text
BehaviorMode.PLAN + PermissionMode.FULL_ACCESS
```

仍然只能执行 PLAN Mode 允许的操作。

# 五、DEFAULT Mode 产品语义

DEFAULT 是正式执行模式。

行为目标：

```text
理解用户目标
  ↓
按需探索
  ↓
按需建立/更新 TaskState
  ↓
实施
  ↓
验证
  ↓
处理失败 / 新事实 / 用户 Steering
  ↓
必要时重规划
  ↓
满足完成条件
```

DEFAULT Mode 必须具备：

- 完整普通 Tool View；
- 正常 Permission 控制；
- `AskUserQuestion`；
- `TodoWrite`；
- Execution Planning；
- User Steering；
- Completion Hook；
- 普通 final / TurnCompleted 语义。

简单任务可以完全不创建 TaskState。

Runtime 不负责判断“这个任务是不是长任务”。是否使用 Todo/Execution Planning 由模型根据任务结构和执行需要决定。

# 六、PLAN Mode 产品语义

PLAN 是独立行为模式。

## 6.1 行为目标

PLAN Mode 的目标链：

```text
理解目标
  ↓
只读探索事实
  ↓
必要时 AskUser
  ↓
形成 decision-complete Plan
  ↓
Plan Proposal
  ↓
用户 Review
  ├─ REVISE  → 同 Turn 继续规划
  └─ APPROVE → 同 Turn 自动进入 DEFAULT 并实施
```

## 6.2 PLAN 不是“禁止写入的 DEFAULT”

PLAN Mode 必须拥有独立的：

- 行为目标；
- prompt section；
- Tool View；
- pre-tool policy；
- final semantics；
- PlanState；
- Plan Review 控制协议；
- TUI Plan projection。

## 6.3 Tool View

当前默认 builtin 条件下，PLAN Provider-facing Tool View：

```text
ReadFile
Glob
Grep
Bash
AskUserQuestion
```

不向 Provider 暴露：

```text
WriteFile
EditFile
TodoWrite
```

`Bash` 虽然可见，但实际调用必须经过 trusted preflight；只有 `PermissionAction.effect == READ` 才能继续。

## 6.4 Plan Approve 自动实施

用户批准 Plan 后：

```text
PLAN
  ↓ APPROVE
PlanState.approved = true
  ↓
BehaviorMode.DEFAULT
  ↓
TurnResumed
  ↓
下一 Provider iteration 使用 DEFAULT prompt + full execution Tool View
  ↓
同一个 active Turn 继续实施
```

用户不需要输入 `/do` 或 `/build`。

# 七、Todo / TaskState

## 7.1 定位

Todo 是执行期结构化工作状态，不是 Plan Mode 的自然语言 Plan。

```text
PlanState  = 用户可审阅的实施方案
TaskState  = 当前执行中的结构化工作事实
```

二者不自动转换。

## 7.2 Core Control Tool：`TodoWrite`

`TodoWrite` 是 Agent 自动路径中的 Core Control Tool。

它不进入普通 Integration `ToolRegistry`，不提供手动 Application Tool API。

Provider schema：

```json
{
  "todos": [
    {
      "content": "修改 AgentLoop completion boundary",
      "status": "in_progress"
    },
    {
      "content": "补 completion tests",
      "status": "pending"
    }
  ]
}
```

状态：

```text
pending
in_progress
completed
```

约束：

- `content` 非空。
- 保持输入顺序。
- 同一时刻最多一个 `in_progress`。
- 可以没有 `in_progress`。
- `todos=[]` 表示明确清空当前 TaskState。
- 不增加 ID、priority、dependency、parent、DAG edge。
- `TodoWrite` 采用 replace-all 语义；一次调用提交当前完整 TaskState。

## 7.3 权威写入

流程：

```text
Provider TodoWrite call
  ↓
Core schema / argument validation
  ↓
Todo update candidate
  ↓
AgentLoop 写 RunState.task_state
  ↓
TaskStateChanged event
  ↓
返回同 call_id ToolResult
```

Tool 本身不直接修改 RunState。

参数错误：

- 返回标准 error `ToolResultPart`；
- TaskState 不变化；
- 当前 Turn 继续。

## 7.4 生命周期

TaskState 是 current Turn local：

- 新 Turn 开始时为空。
- iteration 之间保留。
- Permission Ask/Resume 之间保留。
- AskUser pause/resume 之间保留。
- User Steering 之间保留。
- Plan approve 后若模型进入 DEFAULT，可建立新的 TaskState。
- TurnCompleted / Failed / Cancelled 后不作为下一 Turn 的 active task state 继承。

TaskState 独立于 messages，为未来上下文压缩保留明确边界。

# 八、Execution Planning（持续执行/长任务规划）

## 8.1 定位

Execution Planning 是 DEFAULT Mode 中的持续执行协议。

它不是第二个 AgentLoop，也不是 Runtime Scheduler。

物理执行仍然是：

```text
AgentTurnExecution.run_segment
  → iteration N
  → iteration N+1
  → iteration N+2
```

概念上的 Execution Planning loop：

```text
读取当前目标 + TaskState + 新事实
  ↓
模型选择下一步
  ↓
Tool / AskUser / Reasoning
  ↓
获得结果
  ↓
判断当前计划是否仍然成立
  ↓
更新 TaskState / 重写 TaskState / 继续当前步骤
  ↓
下一 iteration
```

## 8.2 何时建立 TaskState

由模型自行判断。

Prompt 仅要求：当任务存在多个需要持续跟踪的步骤、执行跨度较长、需要在多轮工具调用间保持工作状态时，优先使用 `TodoWrite`。

Runtime 不根据以下指标自动触发：

- Tool call 数量；
- 文件数量；
- 代码行数；
- token 数量；
- 固定关键词；
- 用户文本长度。

## 8.3 执行推进

当存在 TaskState 时，模型应持续做到：

- 当前工作发生变化时更新 `in_progress`；
- 工作真实完成后才标记 `completed`；
- 新发现的必要工作加入当前完整 Todo；
- 已失效工作从当前完整 Todo 中移除；
- 保持 TaskState 与当前真实执行意图一致。

Runtime 只验证结构，不判断 Todo 内容是否“聪明”。

## 8.4 自主重规划

TaskState 是当前最佳执行计划，不是冻结工作流。

当出现新事实时，模型可以整体重写 Todo。

典型重规划条件属于 Prompt 行为语义：

- 初始假设被代码事实推翻；
- 当前实现路径不可行；
- 验证失败暴露新工作；
- 用户 Steering 修改目标或约束；
- AskUser 返回的新信息改变方案；
- 原步骤已不再必要；
- 新依赖或安全边界被发现。

Runtime 不自动判断何时重规划。

## 8.5 失败处理

普通 Tool failure 不直接改变 TaskState。

模型根据失败事实决定：

```text
局部错误可修复
  → 保持当前任务并继续修复

原路径不可行
  → 重写 TaskState

需要用户决策
  → AskUserQuestion

用户目标发生变化
  → 根据 Steering 重新规划
```

## 8.6 与已批准 Plan 的关系

Plan approve 后，`PlanState` 继续作为当前 Turn 的已批准实施依据。

DEFAULT Mode 中模型可以根据实际代码事实调整具体执行步骤与 Todo，但如果调整会改变：

- 用户目标；
- 已批准核心范围；
- 关键架构决策；
- 重要安全语义；

则必须使用 `AskUserQuestion` 请求用户确认。

Plan 不自动转换为 Todo；模型在进入 DEFAULT 后自行决定是否创建 TaskState。

# 九、User Steering

## 9.1 产品定义

User Steering 是 active Turn 运行期间，用户主动追加、修改或收缩当前任务要求的能力。

示例：

```text
用户：完成 1
Agent：正在执行 1
用户：和 2
```

Steering 后当前 Turn 的用户目标语义为：

```text
完成 1
+
和 2
```

最终仍由同一个 active Turn 继续执行。

另一个示例：

```text
用户：完成 1
Agent：正在执行
用户：别做 1 的 B 部分，只做 A，并补 2
```

该文本必须成为当前 Turn 的真实用户事实，模型据此重新审查当前计划。

## 9.2 正式 API

Application `TurnHandle` 新增：

```text
steer(text: str) -> bool
```

语义：

- 仅 active Turn 可调用。
- 输入必须为非空用户文本。
- Steering 请求触发 cooperative interruption。
- 不创建新的 Turn。
- Steering 成功应用后，原 active Turn 继续。

## 9.3 安全中断语义

Steering 必须复用 T06 已存在的“Provider 可中断、Tool 在安全边界处理”的原则。

### Provider generation 中

```text
Provider attempt running
  ↓ User Steering
interrupt current attempt
  ↓
discard uncommitted partial attempt
  ↓
append steering as real user message
  ↓
next iteration
```

被 Steering 中断的 Provider attempt：

- 不提交 candidate assistant final；
- 不提交该 attempt 的不完整 assistant message；
- 不把未完成 attempt 当作 Turn failure；
- 继续同一个 active Turn。

### Tool execution 中

正在执行的普通 Tool 不因 Steering 被强杀。

```text
current Tool finishes at safe boundary
  ↓
remaining not-yet-started ToolCalls in current batch do not execute
  ↓
for each remaining call_id produce controlled skipped/error ToolResult
  ↓
close ToolBatch
  ↓
apply steering user message
  ↓
next iteration
```

这样既避免执行已经过时的后续副作用，又保持 ToolCall ID 闭合不变量。

## 9.4 Steering 写入 Conversation

Steering 文本必须由 AgentLoop 作为真实 `role=user` Message 写入 `RunState.messages`。

不得：

- 伪装为 system message；
- 伪装为 tool result；
- 只存在于 TUI 本地；
- 只存在于一次性 prompt feedback。

同时生成一次性 runtime feedback：

```text
用户已更新当前任务要求；在继续执行前重新审查当前目标、已批准 Plan 与 TaskState，按需更新执行计划。
```

该 feedback 只辅助下一次请求，不替代真实 user message。

## 9.5 与 TaskState 的关系

Steering 不自动修改 Todo。

流程：

```text
steering user message
  ↓
模型重新理解目标
  ↓
读取现有 TaskState
  ↓
保持 / 更新 / 整体重写 Todo
  ↓
继续执行
```

## 9.6 与 PLAN Mode 的关系

PLAN Mode 生成过程中也允许 Steering。

Steering 后：

- 仍保持 PLAN；
- 当前 Plan goal 更新；
- 模型继续只读研究并形成新的完整 Plan。

当已经进入 `PLAN_REVIEW_REQUIRED` pause 时，用户通过 Plan Review `REVISE` 提交修改点；该交互不走普通 Steering 输入路径。

## 9.7 与其它 pending pause 的关系

当 active Turn 正等待：

- AskUser response；
- Permission approval；
- Provider retry decision；
- Plan Review；

Interface 必须优先完成当前 typed interaction；普通输入不能绕过当前 pending pause 直接注入 Steering。

## 9.8 Race / cancellation

优先级：

```text
Cancel > Steering > candidate completion
```

含义：

- 已取消 Turn 不再接受 Steering。
- Steering 已被接受且尚未应用时，candidate final 不得先提交。
- 重复 cancel 幂等。

同一时刻最多存在一个尚未应用的 Steering 请求；应用并恢复后可继续提交下一次 Steering。

# 十、PlanState 与 Plan Review

## 10.1 PlanState

新增 Turn-local `PlanState`：

```text
revision: int
text: str
approved: bool
```

约束：

- 只在 PLAN Mode proposal 时建立/替换。
- revision 从 1 开始递增。
- 每次 REVISE 后生成完整替代版 Plan。
- `approved=true` 后保留到当前 Turn 结束，作为 Execution Planning 的已批准依据。
- 新 Turn 重置。

## 10.2 Plan proposal final semantics

PLAN Mode 下 Provider 的无 ToolCall final 不是 Turn completion。

流程：

```text
candidate final
  ↓
```

# 十一、Runtime Hook

## 11.1 定位

T08 引入第一批有真实生产调用方的 Runtime Hook。

Hook 属于 Core Runtime 生命周期控制扩展点。

Hook 必须满足：

- 默认只读取不可变上下文。
- 仅明确的 pre-hook 可返回结构化控制结果。
- Hook 不主动发起 Agent generation。
- Hook 不主动执行 Tool。
- Hook 不直接修改 RunState。
- AgentLoop 仍是所有 Core 状态写入的唯一 authority。
- Hook exception 不得静默 fail-open。

## 11.2 当前 Hook Point

本任务只定义两个存在当前调用方的 hook point：

```text
before_tool_execution
before_completion
```

建议新文件：

```text
src/uthcode/core/hooks.py
```

不建立目录级插件运行时。

## 11.3 Hook composition

AgentLoop 接收不可变 HookSet：

```text
RuntimeHookSet
  before_tool_execution: tuple[BeforeToolExecutionHook, ...]
  before_completion: tuple[BeforeCompletionHook, ...]
```

Hook 顺序由 Application/Core composition 显式固定。

不提供运行中动态注册、全局单例或 Interface 注册入口。

## 11.4 `before_tool_execution`

执行位置：

```text
ToolExecutor.prepare_call
  ↓
PreparedToolCall
  ↓
before_tool_execution hooks
  ↓
Permission
  ↓
execute_prepared
```

输入上下文至少包括：

```text
run_id
turn_id
behavior_mode
PreparedToolCall
```

结构化结果：

```text
Continue
Reject(error_text, reason)
```

当前生产调用方：PLAN Mode Tool Policy Hook。

## 11.5 PLAN Tool Policy Hook

规则：

```text
if behavior_mode == PLAN:
    prepared.action.effect must be READ
else:
    continue
```

PLAN 中 `WRITE/DESTRUCTIVE/EXTERNAL/UNKNOWN` 直接得到受控 Tool error，不进入 Permission。

`full_access` 不能绕过该 Hook。

## 11.6 `before_completion`

执行位置：

```text
Provider candidate final
  ↓
validated terminal response
  ↓
usage accounting
  ↓
before_completion hooks
  ↓
accept / block / pause
  ↓
只有 accept 才提交普通 assistant completion
```

输入上下文至少包括：

```text
run_id
turn_id
behavior_mode
candidate_text
TaskState
PlanState
```

结构化结果：

```text
Continue
Block(feedback, reason)
RequestPause(kind, payload, reason)
```

Hook 不创建最终 `PauseRequest` ID，也不直接写 pending pause；AgentLoop 根据 `RequestPause` 构造正式 PauseRequest。

Hook 返回控制结果后，由 AgentLoop 负责：

- 更新 `PlanState`；
- 设置 Pause；
- 写事件；
- 写 message；
- 继续 iteration；
- 完成 Turn。

Hook 自身不写状态。

## 11.7 Completion Hook 顺序

当前顺序固定：

```text
1. Plan Completion Hook
2. Task Completion Hook
```

行为：

- PLAN candidate final 首先转成 Plan Proposal / Review Pause。
- DEFAULT candidate final 再检查 unfinished TaskState。

## 11.8 Hook failure

T08 的两个 pre-hook 都参与 Runtime 正确性与安全控制。

若 Hook 内部出现未预期异常：

```text
TurnFailed
```

不得继续 Tool execution 或提交 candidate final。

公开错误保持脱敏，不暴露内部 payload/secret。

# 十三、Completion Control

## 13.1 Task Completion Hook

仅在 `BehaviorMode.DEFAULT` 生效。

如果 TaskState：

- 为空；或
- 所有 item 均 `completed`；

则允许普通 completion。

如果至少一个 item 非 completed：

```text
candidate final
  ↓
Task Completion Hook
  ↓
Block
  ↓
CompletionBlocked event
  ↓
one-shot runtime feedback
  ↓
next iteration
```

## 13.2 blocked final 语义

被 Block 的 candidate：

- usage 正常计入；
- 不写入 `RunState.messages`；
- 不发送普通 `AssistantMessageCompleted`；
- 不产生 `TurnCompleted`；
- 不作为 TUI 最终答案显示。

feedback 指明当前仍存在未完成 Task，并要求模型：

- 继续执行；或
- 如果 TaskState 已失效，先用 `TodoWrite` 更新/重写 TaskState；
- 不得仅为了通过 Guard 把未完成工作虚假标记 completed。

## 13.3 迭代上限

每次 Completion Block 正常消耗下一 iteration。

继续受现有 `max_iterations` 约束，不增加第二套 retry loop。

## 13.4 candidate text buffering

为了保证 UI 真值：

- PLAN Mode 的 assistant candidate text 在 terminal 前缓冲；
- DEFAULT 且当前存在 unfinished TaskState 时，该 iteration 的 assistant candidate text在 terminal 前缓冲；
- ToolCall iteration 在 terminal 判定后可按 progress 输出；
- blocked completion 直接丢弃 candidate final 文本；
- ordinary DEFAULT、无 unfinished Task 时继续使用现有 streaming 行为。

# 十四、Runtime Prompt Facts

## 14.1 Prompt 边界

T08 只完成能力运行所需的最小 prompt 语义。

完整 Coding Agent System Prompt 设计另行任务包处理。

RequestPreparer 扩展为接收窄化的 Runtime Prompt Context：

```text

  behavior_mode
  task_state
  plan_state
  one_shot_feedback
```

不得直接把整个 `RunState`、ToolRegistry、Application 或 UI 对象传入 prompt builder。

## 14.2 DEFAULT 最小行为语义

Prompt 至少说明：

- 当前是实施模式；
- 简单任务无需强制 Todo；
- 需要持续跟踪多步骤工作时使用 `TodoWrite`；
- TaskState 是当前执行事实，应与真实进度保持一致；
- 新事实可能要求更新或整体重写 TaskState；
- Steering 后重新检查当前目标与 TaskState；
- approved Plan 存在时以其为当前实施依据；
- 对批准范围的实质修改需 AskUser；
- 在未完成工作存在时不要声明任务完成。

## 14.3 PLAN 最小行为语义

Prompt 至少说明：

- 当前是规划模式；
- 只研究、澄清、设计，不实施修改；
- 可以使用可见只读 Tool 探索；
- 必要时 AskUser；
- final 应是完整、可独立审阅的 Plan；
- 用户 REVISE 后输出完整替代版 Plan；
- 不使用 Todo 表代替自然语言 Plan。

## 14.4 Steering feedback

Steering 应产生一次性 runtime feedback，提醒模型重新审查：

```text
current user goal
approved Plan
TaskState
next action
```

下一次成功 request 后该 feedback 清除。

## 14.5 Completion feedback

Completion Block feedback 同样为 one-shot fact。

不得通过伪造 user/system/tool Message 注入。

# 二十六、架构验收标准

必须满足：

1. **单 AgentLoop**：T08 不增加另一套规划/长任务执行 Loop。
2. **单状态 authority**：TaskState、PlanState、BehaviorMode 由 AgentLoop 写。
3. **Mode 是真实 Runtime 状态**：不能只由 prompt/tool mask 表示。
4. **Plan 与 Todo 分离**：自然语言 Plan 和结构化执行 Todo 独立。
5. **Execution Planning 由模型主导**：Runtime 不用粗糙复杂度启发式调度。
6. **Steering 同 Turn**：active Turn 新用户要求不默认拆成新 Turn。
7. **Steering 是真实 user fact**：进入 message history。
8. **Tool 安全边界**：Steering 不强杀已执行 Tool，但阻止 stale 后续 call。
9. **Hook 有真实调用方**：当前只实现 pre-tool / pre-completion。
10. **Hook 受限拦截**：不主动执行 Agent/Tool，不直接写 RunState。
11. **Plan Policy 在 Permission 前**：full_access 不能绕过 Plan read-only boundary。
12. **Completion 在 commit 前拦截**：blocked final 不成为权威会话内容。
13. **Plan approve 自动实施**：same Turn `PLAN → DEFAULT`。
14. **Permission 正交**：Behavior Mode 不进入 `PermissionMode` 枚举。
15. **Interface 只投影**：TUI 不拥有 Task/Plan/Mode authority。
16. **未来上下文边界正确**：TaskState/PlanState 不依赖旧 messages 才能存在。

