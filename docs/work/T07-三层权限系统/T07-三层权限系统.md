## 2. 当前实现基线

### 2.1 Tool 边界

当前：

```text
ToolRegistry
→ 查找 Tool
→ JSON Schema 参数校验
→ Tool.execute()
```

`src/uthcode/core/tool.py` 的 `ToolExecutor.execute_call()` 同时承担注册检查、参数校验和真实执行。

T07 权限判断必须满足：

```text
Tool 是否已注册
→ 参数是否合法
→ 无副作用 Action preflight/classification
→ Permission
→ execute
```

因此必须整理一个正式的“已校验但未执行”边界：

- 不复制第二份 JSON Schema 校验；
- 未注册 Tool 继续走现有 unknown ToolResult；
- 参数非法 ToolCall 直接返回参数错误 ToolResult，不触发权限 Ask；
- Permission 通过后执行同一次已校验调用；
- Permission resume 不重复执行任何有副作用的前置逻辑。

### 2.2 Agent Loop 接入点

当前 Tool Batch 的稳定顺序为：

```text
ToolStarted
→ AskUserQuestion 特殊控制路径 / 普通 ToolExecutor
→ ToolFinished
→ ToolResult
→ 下一个 ToolCall
```

T07 在普通已注册 Tool 的真实执行前插入权限判定。

保持：

- FIFO；
- 每个 ToolCall 恰好一个 ToolResult；
- 单个 reject/deny 不终止整个 Run；
- AskUserQuestion 仍是 T06 控制能力，不进入普通 Tool Permission 分类；
- Agent Loop 仍是 RunState 唯一写入者。

### 2.3 T06 Pause/Resume

当前已经存在：

```text
Core AgentTurnExecution
→ PauseRequest
→ Application _TurnDriver
→ TurnHandle.pending_pause / resume()
→ TUI / Headless 提交类型化响应
→ 同一 Turn 恢复
```

T07 扩展现有交互协议，新增 Permission Approval 类型，不重写 T06。

### 2.4 WorkspacePathResolver

当前 `src/uthcode/integrations/tools/workspace.py`：

```text
lexical normalize
→ physical resolve
→ _require_within(workspace)
→ outside workspace 直接 WorkspacePathError
```

需要保留：

- `..` lexical normalize；
- symlink physical resolution；
- 新目标最近已有父目录解析；
- Windows 路径归一；
- `FileReadTracker` 的 read-before-write / changed-since-read。

需要删除的职责：

```text
outside workspace → Tool 层硬拒绝
```

改为：

```text
physical path
→ inside / outside Resource Scope
→ Permission Strategy / Rules
```

### 2.5 Bash

当前 `BashTool` 明确使用：

```text
current OS shell
current OS user privileges
cwd = workdir
```

其进程树终止机制只用于取消与清理，不构成 OS Sandbox。

T07 的 Guard、regex、Action classifier 均属于应用层审批机制，不得在代码、事件、文档或提示中描述为安全隔离。

### 2.6 配置发现

`src/uthcode/integrations/config/loader.py` 已有：

```text
user config
→ Git root 到 cwd 的项目 config 递归发现
→ physical normalize
→ dedupe
→ 越靠近 cwd 越具体
```

T07 的 permission rule discovery 必须复用/提取这套语义，不复制第二套 Git root/cwd 遍历算法。

`permissions.toml` 与 `config.toml` 保持独立。

### 2.7 Slash Command

现有 Slash Command 由 Application Registry / Dispatcher 统一管理。

T07 新增 `/permission` 时：

- 继续使用唯一 Registry；
- mode 属于当前 AgentRun/Application session 状态；
- TUI 不保存 authoritative PermissionMode；
- 不建立第二套命令分发器。

## 3. 当前任务目标

### 3.1 最终交付能力

建立统一三层权限模型：

```text
Action
→ Rules
→ Strategy
→ PermissionDecision
→ ASK 时进入 HITL
```

三层分别回答：

```text
Action   ：这次 ToolCall 实际在做什么？
Rules    ：用户是否对该动作定义了额外约束？
Strategy ：当前 Permission Mode 对未被规则终结的动作默认怎么处理？
```

HITL 是 ASK 的交互出口，不作为第四层。

### 3.2 最小完整调用链

```text
Provider normalized ToolCall
        ↓
Agent Core Tool Batch
        ↓
ToolRegistry registered check
        ↓
JSON Schema validation
        ↓
trusted Tool Action preflight
        ↓
Permission Rules
   Guard → Policy
        ↓
Permission Strategy
        ↓
ALLOW ───────────────→ execute validated Tool
DENY  ───────────────→ error ToolResult → next ToolCall
ASK   → T06 PauseRequest
            ↓
       Application TurnHandle
            ↓
      TUI / Headless response
            ↓
        same Turn resume
            ↓
 allow once / session / reject
```

### 3.3 权限模式

固定为：

```text
default
auto
full_access
```

最终行为矩阵：

| 场景 | default | auto | full_access |
| --- | --- | --- | --- |
| workspace 内普通 READ | allow | allow | allow |
| workspace 内普通 WRITE | ask | allow | allow |
| workspace 外普通 READ | ask | ask | allow |
| workspace 外普通 WRITE | ask | ask | allow |
| DESTRUCTIVE | ask | ask | allow |
| EXTERNAL | ask | ask | allow |
| UNKNOWN | ask | ask | allow |
| Policy ALLOW | allow | allow | 忽略 Policy |
| Policy ASK | ask | ask | 忽略 Policy |
| Policy DENY | deny | deny | 忽略 Policy |
| Guard ASK | ask | ask | ask |
| Guard DENY | deny | deny | deny |
| Guard ALLOW | 跳过该 Guard，继续 Policy/Strategy | 跳过该 Guard，继续 Policy/Strategy | allow |

`full_access` 定义：

```text
普通 Tool 行为不再审批
≠ 关闭 Guard
≠ OS Sandbox
≠ 提升操作系统权限
```

### 3.4 Effect

固定最小集合：

```text
READ
WRITE
DESTRUCTIVE
EXTERNAL
UNKNOWN
```

Effect/Action 是 UthCode 内部可信执行事实：

- 不进入 Provider-facing `ToolDefinition`；
- 不允许 LLM ToolCall 参数声明或覆盖；
- 简单 Tool 可固定；
- Bash 等复合 Tool 根据参数动态分类；
- 无法可靠判断时必须为 `UNKNOWN`。

六个当前内置普通 Tool 至少覆盖：

```text
ReadFile
WriteFile
EditFile
Glob
Grep
Bash
```

### 3.5 Out of Scope

不实现：

```text
OS / Container / Path / Network Sandbox
seccomp / bubblewrap / Seatbelt / Windows OS Sandbox

Skill / MCP / Hook
Subagent / Multi-Agent / Worktree

Plan Mode / Todo Tool / 长任务规划
Context / Memory

AI Permission Reviewer
自动权限学习
规则热重载
Allow always / Deny always
/permission add / reset
Plugin Permission API
Credential Broker 完整系统
完整 Bash / PowerShell AST 安全解析器
```

不得为上述能力提前创建空 Protocol、Adapter、Registry、字段或目录。

## 8. 依赖与数据流

### 8.1 模块依赖

固定方向：

```text
interfaces
    ↓
application ─────────→ integrations
    ↓                     ↓
   core ←─────────────────┘
```

Permission 具体要求：

```text
core/permission.py
    不读取 TOML
    不访问 filesystem
    不依赖 TUI
    不依赖 Provider SDK

integrations/permissions.py
    读取/创建 permissions.toml
    编译验证 regex
    转换为 Core Rule values

integrations/tools/*
    提供 trusted Action/Resource facts
    不自行决定 default/auto/full_access

application/runs.py
    拥有当前 Run 的 PermissionMode + SessionGrant 生命周期

interfaces/*
    只显示 Application 暴露的状态/请求并提交响应
```

### 8.2 Tool 数据流

```text
ToolCallPart
→ ToolRegistry.lookup
→ schema validate
→ Prepared/Validated ToolCall
→ trusted Action classification
→ PermissionAction
→ PermissionEvaluator
→ Decision
```

`PermissionAction` 至少表达：

```text
tool
action
effect
resource summary
workspace scope
```

resource 必须是规范化、可安全展示的事实，不得包含 secret value。

### 8.3 Rules 决策顺序

规则文件：

```text
~/.uthcode/permissions.toml
<project>/.uthcode/permissions.toml
```

Git 项目：

```text
Git root/.uthcode/permissions.toml
→ ...
→ cwd/.uthcode/permissions.toml
```

非 Git：

```text
cwd/.uthcode/permissions.toml
```

来源优先级：

```text
nearest project
>
parent project
>
user
>
default template
```

Rule 文件必须分：

```text
Guard Rules
Policy Rules
```

决策：

1. 先确定最高优先级、存在匹配的有效来源；
2. 在该来源同类多个匹配中使用：

```text
DENY > ASK > ALLOW
```

不得把“来源优先级”和“同一来源冲突严格度”混成全局 deny wins。

### 8.4 Guard 精确语义

Guard 三模式全部生效。

```text
Guard DENY  → 最终 deny
Guard ASK   → 最终 ask，不允许 session grant
Guard ALLOW → 仅表示当前 Guard 不再阻挡
```

后续：

- `full_access`：Guard ALLOW 后按 full_access 直接 allow；
- `default/auto`：Guard ALLOW 后继续 Policy，再继续 Strategy。

这一定义为唯一语义，禁止实现成“Guard ALLOW 在 default/auto 中也直接终结所有普通规则”。

### 8.5 Session Grant

Session Grant：

```text
仅由 ordinary ASK 的 Allow for session 产生
只活在当前 AgentRun
新 Run 不继承
不写 config.toml
不写 permissions.toml
```

至少支持：

1. 精确 Tool / Tool Action；
2. outside workspace 文件操作的精确物理目录范围。

必须绑定必要维度：

```text
tool + action + effect + bounded resource scope
```

优先级：

```text
Guard / explicit DENY
>
Session Grant
>
Strategy ASK
```

Session Grant 不得覆盖 Guard ASK/DENY 或 Policy DENY。

### 9.1 生命周期

用户级文件不存在时自动创建：

```text
~/.uthcode/permissions.toml
```

包含：

- Guard 区；
- Policy 区；
- 默认 Guard 种子；

- 可手工编辑示例。

项目级当前 workdir 文件不存在时创建空占位：

```text

```

内容只需类似：

```toml
# Project-specific permission rules.
```

父目录已有 permission 文件继续递归加载。

不实现热重载；RuleSet 在 Application/Run 初始化时形成稳定快照。

### 9.2 Rule 错误

以下全部硬失败，不得静默跳过：

- TOML 无法解析；
- 未知 effect；
- regex 无法编译；
- 必要字段缺失；
- 规则无法确定匹配目标；
- Guard / Policy 结构非法。

### 9.3 默认敏感资源 Guard

至少覆盖内容访问/内容搜索/编辑写入：

```text
.env
.env.*
.env.example 例外

~/.ssh/**
~/.aws/credentials
~/.config/gcloud/**
~/.azure/**
~/.kube/config
~/.docker/config.json
~/.config/gh/hosts.yml
~/.git-credentials
~/.netrc
~/.npmrc
~/.pypirc

*.pem
*.key
id_rsa
id_ed25519
常见 private key 文件名
```

普通 metadata 行为：

```text
exists
stat
文件名枚举
```

不应自动等同于读取 secret 内容。

Grep/内容搜索必须走可确定的 sensitive-resource 保护，禁止出现：

```text
ReadFile(.env) → ask
Grep(path=".") → 直接把 .env 内容送给模型
```

### 9.4 默认高置信 Bash Guard

默认 Guard ASK 至少覆盖：

```text
递归删除 filesystem root / user home / workspace root
当前目录明显全量递归删除通配

mkfs / wipefs
fdisk / parted 等真实磁盘破坏
写 /dev/* 块设备
dd 覆盖块设备

fork bomb

sudo / su 提权入口

root/home 递归 chmod/chown
明显极端 777 权限修改

curl | sh
wget | sh
等下载后直接执行

kill/pkill 指向 PID 1、-1 或高置信关键系统目标

Windows：
format
diskpart clean
Clear-Disk
Format-Volume
系统盘/用户目录/workspace root 递归强制删除
```

负例：

```text
rm -f
kill -9 <普通 PID>
rm -rf build/
```

不得仅因为命令字符串出现 `rm -f` / `kill -9` 就判为 Guard。

它们仍可被 Bash classifier 判为 `DESTRUCTIVE`，再由 default/auto Strategy ASK。

### 9.5 命令匹配边界

- regex 作用于规范化后的动作/命令表示；
- Guard 不能假装简单字符串匹配等于完整 Shell 解析；
- 对可确定的 `&& / || / ; / |` 复合段，必须避免安全前缀掩盖危险后段；
- 不实现完整 Bash/PowerShell AST；
- 无法可靠分类时 `Effect = UNKNOWN`；
- 测试危险 Guard 只能 mock/stub execute，不得执行真实危险命令。

- Provider SDK 类型不进入 Permission；
- no LangGraph；
- no Skill/MCP/Hook/Sandbox/Plan/Todo placeholder。

## 14. 删除与清理

T07 结束时删除/替换以下遗留职责，而不是保留兼容分支：

1. `WorkspacePathResolver` 中“outside workspace 必然 error”的授权职责；保留规范化和物理解析职责。
2. `ToolExecutor.execute_call()` 中无法插入授权的单体执行边界；改成唯一 validated/prepared → execute 流程，不保留双入口长期并存。
3. 若接入过程中创建临时 permission wrapper/adapter，主流程接通后删除。
4. 与旧 full_access 语义冲突的 `SRe-AGENTS.md` 文本。
5. 任何自动 persistent exact decision 逻辑或 always 按钮占位。
6. 任何 `permissions.yaml` / local rule / PathSandbox / L1～L5 兼容实现。
7. 任何 TUI authoritative Permission Store 或第二套 Slash Command dispatcher。

不得删除与 T07 无关的历史能力。

## 15. 验收标准

全部满足才视为完成：

1. 六个内置普通 Tool 均在参数校验后、真实副作用前得到 trusted `PermissionAction`。
2. 未注册 Tool 和参数非法 Tool 不产生 Permission Ask。
3. Action → Guard/Policy Rules → Strategy 是唯一生产权限链，无五层/L1～L5 双轨。
4. `default / auto / full_access` 行为与本文矩阵完全一致。
5. `full_access` 忽略普通 Policy/Strategy 审批，但 Guard ASK/DENY 仍有效。
6. Guard ALLOW 的语义唯一：default/auto 继续 Policy/Strategy；full_access 放行。
7. outside workspace 不再被原生 Tool 硬拒绝；default/auto 可 Ask 后执行，full_access 普通操作可执行。
8. symlink、`..`、新目标和 Windows 路径均按最终物理资源分类。
9. `.env`、SSH/cloud/credential/private-key 等敏感内容访问受 Guard；Grep 不可旁路。
10. Bash 至少稳定分类常见 git/read/write/destructive/external；无法确认时 UNKNOWN。
11. 高置信 Bash Guard 有正反例测试，且不实际执行危险命令。
12. ordinary Ask 提供 once/session/reject；Guard Ask 只有 once/reject。
13. Session Grant 仅当前 AgentRun 有效，不覆盖 DENY/Guard，不泛化到宽目录/任意 action。
14. Permission Ask 复用 T06 `PauseRequest → TurnHandle.pending_pause/resume()`，没有第二套异步协调机制。
15. deny/reject 后生成标准 error ToolResult，同 batch 后续 ToolCall 继续。
16. `/permission` 使用现有 Slash Command Registry，mode 不持久化，full_access 只能由用户主动切换且有风险提示。
17. TUI 只调用 Application 公共 API；CLI 不自动批准；Headless 可独立完成 Permission round trip。
18. Permission metadata 不进入 Provider ToolDefinition；Provider SDK 类型不进入 Core。
19. `permissions.toml` user/project 生命周期、递归发现、来源优先级、regex/TOML 错误行为均有自动测试。
20. 不宣传 Guard/regex/Bash classifier 为 OS Sandbox。
21. T04/T05/T06 回归通过，三 Provider 集成行为一致。
22. 架构扫描证明无 LangGraph、旧权限模式、PathSandbox、Skill/MCP/Hook/Sandbox/Plan/Todo 未来占位。
23. 全量测试、compile、依赖检查、diff/编码检查通过。
24. 当前公共边界可以直接作为后续 Context/Memory/Skill/MCP 等任务的真实基线，无需推翻 Permission Core。

## 16. 编码停止条件

出现以下情况必须停止相关实施并报告：

- 与 `AGENTS.md` 或本文冻结语义冲突；
- T04/T05/T06 正式任务包与 `cab4c0a...` 实际代码存在新的实质差异，且会改变 Permission 公共边界；
- 必须重写 T06 暂停核心语义，而不是扩展其类型化协议；
- 需要让 Core 依赖 TUI、Integration、TOMLKit 或 Provider SDK；
- 需要让模型声明/修改自己的 Effect；
- 需要扩大到 OS Sandbox、Plan/Todo、Skill/MCP/Hook、Subagent/Multi-Agent；
- 需要建立 Plugin Permission API 或未来扩展占位才能继续；
- Session Grant 只能通过宽泛授权实现，无法保持精确有界；
- Tool 是否已产生副作用无法确认，禁止盲目 retry；
- 需要完整 Shell AST / 通用工作流引擎才能推进；
- 实际改动范围明显超出本文文件职责；
- 两项冻结决策发生新的实质冲突。

以下不属于停止条件，编码代理应自行解决：

```text
普通文件命名
私有函数拆分
fixture 组织
regex 具体写法
最小 TOML table 结构
普通编译错误
测试失败
局部实现缺陷
可轻易替换的 stdlib 级工程细节
```
