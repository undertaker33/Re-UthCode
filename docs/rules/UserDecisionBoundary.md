## 用户拍板边界

Agent 默认自行完成授权范围内的工程判断，并持续推进到交付。

### 判断条件

只有同时满足以下两项，才需要用户拍板：

1. 决定会实质影响产品语义、长期公共边界、任务范围、安全边界或已冻结设计。
2. 无法由 `AGENTS.md`、用户已拍板决定、正式任务书和当前真实代码确定答案。

先结合现有代码、冻结边界、当前调用方和最小完整需求收敛。已有授权或决定足以确定下一步时，不重复请求确认。

### 需要拍板的情形

以下情形按上述双条件判断；已经明确授权的改动直接执行：

- **产品或安全语义未定**：例如自动执行与确认、失败后继续与停止、状态跨 Turn / Run 保留、取消与恢复，以及危险操作、权限扩大或外部副作用的授权。
- **长期公共设计需要决定**：修改冻结 API、Core 模型、状态所有权或模块依赖；新增系统级架构、生命周期或持久化体系；引入锁定核心设计的依赖、协议或长期兼容层。局部可替换抽象不属于此类。
- **范围或既有依据冲突**：必须增加另一个独立能力；真实代码与任务书关键前提不符且需要改变目标、公共设计或规定修改范围；当前任务违反冻结约束；两项用户决定互相冲突。

不得自行绕过冻结约束、静默废弃用户决定或通过兼容层化解冲突。冻结工作包的问题按 `WorkPackageRules.md` 在 Feedback 中记录并交由用户决定，不修改冻结文件。

### 自行处理的工程问题

不改变产品语义、公共边界、任务范围或长期架构承诺，且替换成本低的选择，由 Agent 采用符合现有实现的最简单方案。例如局部文件组织、私有函数与数据结构、内部算法和错误处理、测试组织、类型标注、格式、日志文案及可替换的内部依赖。

普通编译错误、测试失败和局部缺陷在当前范围内修复。“有多种写法”“以后可能扩展”“更优雅或通用”以及其他项目采用不同方案，本身都不足以请求拍板。

### 暂停与输出要求

- 仅暂停依赖该决定的范围，继续完成可独立推进的已授权工作；不得以准备方案为由实施尚未获授权的变更。
- 请求前完成必要的证据核查与方案整理，提供具体、可审查的选择；不把普通设计工作转交用户。
- 简明说明问题、为何现在必须决定、现有证据、最多三个方案及其直接影响、推荐方案和理由，以及用户需要做出的最终选择。
- 若暂停源于某条规则，指出具体文件和条款，并解释当前任务为何触发它。
