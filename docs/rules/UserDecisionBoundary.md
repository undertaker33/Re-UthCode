## 用户拍板边界

Agent 的默认职责是自行完成工程判断，而不是把普通实现选择交还给用户。

只有当一个问题同时满足以下条件时，才属于“需要用户拍板”：

```text
该决定会实质影响
产品语义 / 长期公共边界 / 任务范围 / 安全边界 / 已冻结设计

并且

无法由现有 AGENTS.md、用户已拍板决定、正式任务书、当前真实代码唯一推出答案
```

### 必须停止并请求用户拍板

以下情况不得自行决定：

1. **产品行为存在真实歧义**

   不同方案会导致用户可观察行为不同，例如：

   ```text
   是否自动执行
   是否要求确认
   失败后继续还是停止
   状态是否跨 Turn / Run 保留
   用户是否可以取消、覆盖或恢复
   ```

2. **核心状态所有权存在架构分歧**

   无法从已有边界确定某项核心状态应由谁创建、持有和修改，并且不同选择会改变模块职责或公共协议。

3. **必须修改已冻结公共边界**

   包括但不限于：

   ```text
   公共 API
   公共 Protocol
   Agent Core 核心模型
   Application API
   模块依赖方向
   已冻结产品语义
   ```

4. **需要新增系统级架构机制**

   例如新增：

   ```text
   新的架构层
   全局事件总线
   通用 Registry / Manager
   新的生命周期体系
   新的持久化状态体系
   ```

   局部内部抽象不属于此类。

5. **两个合理方案会形成不同的长期公共设计**

   即当前选择一旦被后续能力依赖，未来切换需要大规模迁移、兼容或破坏性修改。

6. **当前任务需要扩大到另一个独立能力才能成立**

   例如实施 TXX 时发现必须同时完成另一个原本独立规划的能力，而不是增加少量必要配套代码。

7. **当前任务与既有冻结约束发生实质冲突**

   不得通过绕过、兼容层或“先这样实现”自行化解。

8. **两项用户已拍板决定互相冲突**

   Agent 不得自行判断哪一项优先，也不得静默废弃其中一项。

9. **涉及新的安全或权限边界**

   例如：

   ```text
   是否允许某类危险操作
   是否绕过权限检查
   是否扩大 full_access 权限
   是否暴露敏感数据
   是否允许未经确认的外部副作用
   ```

10. **引入会锁定核心设计的外部依赖或协议**

    只有当依赖会进入长期公共边界、使 Core 与特定实现强绑定，或未来替换成本显著时需要拍板。

11. **真实代码与任务书的关键前提不一致**

    且继续实施需要改变任务目标、公共设计或文件修改范围，而不是普通实现修正。

12. **发现需要长期兼容层或历史包袱**

    当前项目原则上不应为了旧实现增加长期兼容逻辑；如果确有必要，必须由用户明确决定。

------

### 不需要用户拍板

以下属于 Agent 应自行解决的工程问题：

```text
文件名与目录内局部组织
私有类 / 私有函数拆分
普通数据结构选择
内部算法实现
局部错误处理
异常类型的内部组织
fixture / mock / 测试组织
测试用例拆分
类型标注
lint / format
日志文案
注释
普通性能优化
低成本可替换的内部依赖
不改变产品语义的重构
编译错误
类型错误
单元测试失败
局部实现 Bug
```

即使存在多个可行方案，只要：

```text
对用户不可观察
不改变公共边界
不改变任务范围
不形成长期架构承诺
替换成本低
```

Agent 应自行选择最简单、最符合现有代码风格的方案。

------

### 不得制造“伪拍板问题”

以下理由本身不足以请求用户决定：

```text
“有两种写法”
“以后可能扩展”
“哪个更优雅”
“哪个更通用”
“某成熟项目用了另一种方案”
“未来 Skill / MCP / Multi-Agent 可能需要”
“我不确定文件应该放哪里”
```

Agent 必须先根据：

```text
现有代码
→ 已冻结边界
→ 当前真实调用方
→ 最小完整需求
```

自行收敛。

只有无法收敛且确实触及上述“必须拍板”边界时，才请求用户。

------

### 拍板问题的输出要求

请求用户拍板时，不得只提出开放式问题。

每项必须说明：

```text
问题是什么
为什么当前必须决定
现有证据是什么
方案 A 及直接影响
方案 B 及直接影响
必要时方案 C
Agent 推荐方案及理由
用户只需要回答的最终选择
```

最多提供三个方案。

不得把大段架构设计工作转嫁给用户。

------

### 判断口诀

遇到不确定事项时按以下顺序判断：

```text
能从已有约束推出？
        │
       是
        ↓
    Agent 自行决定

       否
        ↓
是否改变产品语义 / 公共边界 /
任务范围 / 安全边界 / 冻结设计？
        │
       否
        ↓
    Agent 自行决定

       是
        ↓
   请求用户拍板
```
